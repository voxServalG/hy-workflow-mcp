# Release acceptance pressure test

`npm run test:acceptance` is the release-only, fail-closed acceptance gate. It is intentionally not part of `npm test`: unit, end-to-end, and contract tests stay offline and deterministic, while acceptance validates the shipped npm tarball against real repositories and client command boundaries.

## Fixed boundary

For a local run, the runner executes a clean `npm pack`. For a release run, the workflow creates the one canonical `.tgz` first and passes its path through `--package-archive`; the runner must consume that file instead of packing again. It installs that `.tgz` plus the pinned `@voxstudio/docs-gardener@1.0.0-next.0` package into an isolated npm prefix and invokes only the installed commands. The exact companion install uses npm's bounded fetch retries and at most two outer attempts against the same isolated cache; it never substitutes local source. The runner never imports the working-tree runtime as the product under test. The seven repositories, HTTPS URLs, full commit hashes, expected ecosystems, branches, code directories, and documentation roots are fixed in `test/acceptance/matrix.json`.

Changing a URL or commit is a reviewed contract change. Following a repository's moving default branch is forbidden. HTTPS fetches use HTTP/1.1 and at most three attempts for transient network failures; each attempt still requests only the same full commit hash. Exhaustion, authentication failure, or a missing commit fails the release gate.

Local pressure runs can point any matrix entry at an existing read-only clone without changing the canonical HTTPS origin or pinned commit. The two private maintained repositories normally need this locally:

```sh
HY_ACCEPTANCE_MAGNET_MIRROR=/absolute/path/to/magnet-field-modulation-refactor \
HY_ACCEPTANCE_DOCS_GARDENER_MIRROR=/absolute/path/to/docs-gardener \
npm run test:acceptance
```

The other optional inputs are `HY_ACCEPTANCE_VITE_MIRROR`, `HY_ACCEPTANCE_FLASK_MIRROR`, `HY_ACCEPTANCE_EXPRESS_MIRROR`, `HY_ACCEPTANCE_GH_CLI_MIRROR`, and `HY_ACCEPTANCE_RIPGREP_MIRROR`. Each mirror must be a Git directory containing the exact contracted commit. The harness validates that commit and fetches only it through a local `file:` URL; dirty working-tree files are ignored and never copied. Without an input, local runs use the bounded canonical HTTPS fallback. The release workflow checks out all seven fixed commits first, then gives the harness only local paths so product pressure is not coupled to repeated large smart-HTTP transfers. The repository must define `ACCEPTANCE_REPOS_TOKEN` as a fine-grained, read-only GitHub token with Contents access to exactly the two private repositories; public checkouts use no additional secret. Every checkout disables credential persistence, and the acceptance process receives paths, never tokens.

## Isolation and safety

Every run creates one directory below the OS temporary directory and supplies an allowlisted environment to child processes. `HOME`, XDG config/state/cache, `CODEX_HOME`, OpenCode config, npm prefix, npm cache, an empty npm user config, client state, repositories, and reports all live below that directory. Authentication variables and SSH agents are not inherited. On Linux the allowlisted PATH prefers `/usr/bin` and `/bin` so required OS language runtimes cannot be shadowed by mutable `/usr/local` installations. A finite Codex/Claude/OpenCode command stub covers only version and MCP definition inspection/mutation; a `gh` stub rejects remote operations. The harness itself rejects `git push`, `gh pr`, release upload, and npm publishing. Recursive workspace usage is checked after every pinned repository and at completion, never follows symlinks, and fails above 2 GiB; current and peak bytes are included in the report. The release profile has a 45-minute internal budget; the formal verifier grants that budget plus cleanup allowance, and either timeout aborts future spawns, terminates the complete child process tree on POSIX and Windows, waits for the active run to settle, and only then writes the final report.

The source repositories remain at their fixed HEAD and remote refs. Setup may change `hy-workflow.json` and `.github/workflows/hy-workflow.yml`, and may create or migrate the managed block inside `AGENTS.md` (content outside the `<!-- hy-workflow-rules -->` markers must remain byte-for-byte identical). For a legacy fixture, the harness verifies that setup auto-migrates a stale managed AGENTS block instead of refusing to run, and that removal of only the two target MCP tables from project `.codex/config.toml` remains an explicit human boundary; setup and unset never edit the Codex project file. Unset must leave the team artifacts intact and remove the project deployment/config/state/cache, registry record, ownership entries, transaction journal, and owned global client definitions. No `.hy/`, new client project directory, compatibility JSON, compiled output, commit, branch, push, PR, or release artifact is allowed.

## Mandatory scenarios

The release profile has no optional or skipped cases. It covers a recognizable PTY intro and clean cancellation; dry-run; stale managed-rules auto-migration of `AGENTS.md`; project-level Codex and OpenCode shadow refusal; initial/repeated setup; offline doctor; substantive MCP document reads within the 48k-character policy; real doclint and codelint scans on every pinned repository; artifact drift on the three team artifacts (`hy-workflow.json`, `.github/workflows/hy-workflow.yml`, and the managed `AGENTS.md` block); unset; 32 concurrent setups; failure injection at every persisted resource with exact project and user-state rollback; tarball contents; process and disk limits; remote-write rejection; and worktree boundaries. The 32-process burst must produce at least one successful owner transaction; every other initial response must either succeed or be the structured retryable `SETUP_LOCK_BUSY` result, never a timeout or another error. One clean retry after contention must then succeed and prove final convergence without a stranded lock or journal. Failure injection uses a test-only child that sets the process-local internal hook before importing the installed tarball's `dist/setup-cli.js`; production CLI execution never reads a failpoint environment variable.

The lint pressure child imports `checks.js`, `config.js`, and `project-profile.js` from the globally installed acceptance tarball and consumes the same immutable codeload tarballs used by the generated workflow. Preparation downloads each full-commit HTTPS archive with curl's three bounded HTTP/1.1 attempts, verifies the SHA-512 exported by the installed package, and lets npx resolve its registry dependencies from that local archive. The outer preparation has at most two 240-second attempts; a verified archive survives a dependency retry and is never downloaded twice. Every repository scan then runs the same local archive through `npx --offline --package` with a strict 120-second tool budget, so network cold starts cannot masquerade as scan failures or weaken the scan timeout. The child materializes compatibility JSON through the installed runtime. Every result must be parseable JSON with non-negative error/failure counts. Doclint must report a boolean `ok`, a `failed` count, and more than zero scanned files. The pinned codelint supports Python and Rust: those projects must expose installed project-profile evidence for supported code and report more than zero scanned files. JavaScript, TypeScript, and Go projects must still prove that configured project code files exist, while codelint must return a structured zero-count invocation recorded as `notApplicable`; that is N/A, never a clean scan. Native codelint output may omit `ok`; an explicit `ok: false` is accepted only for an OSS target when positive finding counts agree with a failing native exit. A timeout, signal, crash, malformed report, unsupported-file scan, or clean-report/status contradiction fails acceptance. Maintained legacy targets must be clean whenever the tool applies. Popular OSS repositories may legitimately report rule findings, but an applicable scan must complete and expose those findings rather than producing a false green. Before and after each command, existing `codelint.json`, `doclint.json`, and `docs-gardener.json` bytes must match exactly, and absent files must remain absent.

The checked-in and packaged workflows are byte-identical and expose one required `Verify` job plus an independent `Windows Smoke` job. Verify provisions Node unconditionally because mandatory doclint/codelint run for every ecosystem. Windows Smoke is job-level gated to this package repository so downstream projects see a skip instead of an empty green job. Here it runs `npm ci`, builds, executes Windows-safe focused tests, packs exactly one tarball, installs that tarball with docs-gardener in an isolated prefix, then exercises installed setup, repeated setup, and unset. It retains the two shared project artifacts, leaves no project-local runtime or compatibility files, and uploads no compiled output.

A missing required `ok: true`, count, required `Verify` check, timeout, partial result, skip, unexpected zero-file applicable scan, unsupported-file scan, nonzero command, unexpected worktree path, stale local deployment, or recovery without structured evidence fails the gate. A candidate documentation directory must contain at least one `.md` file that mandatory doclint can scan; an RST-only `docs/` directory falls back to a root `README.md`, and a project with neither fails configuration instead of generating an empty green check. Generated project workflows grant the GitHub token only `contents: read`.

Node projects with a lockfile use the matching frozen install. A package with real check scripts but no lockfile uses `npm install --no-package-lock` before those scripts, so setup produces a reviewable CI path without modifying the checkout or pretending `npm ci` can work. The inferred command remains subject to the setup CI confirmation gate.

## Release use

The trusted-publishing workflow pins its npm CLI and first validates that the exact release tag commit is checked out, belongs to `origin/main`, and has semver prerelease state matching the GitHub release type. It then runs `npm ci` and the normal verification suite, creates exactly one release tarball, records its SHA-512, passes that exact tarball into this complete acceptance profile, verifies the bytes are unchanged, and publishes the same file with `next` or `latest`. Publishing the source directory after acceptance is forbidden. Reports are printed as NDJSON and written only below the temporary acceptance workspace. The workflow never uses `actions/upload-artifact`, never commits `dist/`, and never attaches compiled output to GitHub.
